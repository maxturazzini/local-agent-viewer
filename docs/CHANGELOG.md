The five orphaned `destroyChart('skillsPie'|'subagentsBar'|'subagentsPie'|'mcpServer'|'mcpTools')` calls were removed with them — left behind they would have been silent no-ops forever. LAV-83: the claude.ai parser read `is_error` and threw it away — outcomes recovered with no new export.
- **Problem**: `lav/parsers/claude_ai.py:_render_content_block` reads `cont.get("is_error")` off every `tool_result` block and uses it **only** to compose the string `--- tool_result: NAME (ok|error) ---` inside the message body. The `mcp_tool_calls` INSERT stores neither `is_error` nor `tool_call_id`. Result: every claude.ai row sat at `is_error IS NULL` — "never measured" — dragging the table's apparent coverage down and hiding the failures entirely. The outcome of every claude.ai tool call was in the database **as prose**, in a column no query can aggregate.
- **Recovered from the markers already stored**, because the original export folder is not guaranteed to still exist on disk — requiring a fresh account export would have been the only alternative. New `lav backfill claude-ai-outcomes`.
- **Algorithm**: one whole-line-anchored MULTILINE regex (`^--- tool_(use|result): (.+?)(?: \((ok|error)\))? ---$`, so a transcript pasted *into* a conversation cannot match mid-line), tool names normalised with `split(':')[-1]` (the export renders result names qualified as `<integration>:<tool>`), then a **FIFO of open `tool_use` ranks per normalised name**, popped oldest-first by each result. The obvious alternative — counting results per name — pairs about 90% of them; the FIFO survives interleaved calls of different tools and pairs **100%, with zero orphans**.
- **Measured on a real corpus**: **99,1% of the paired results land on a real row**, and the residual `unmatched_rank` (more markers than rows — a quoted transcript, or a call whose row was never written) is counted, never guessed at. The rows left at `is_error IS NULL` afterwards are correct: their call has no result, which is exactly what NULL means. Re-running stamps **0**: the `AND is_error IS NULL` guard makes it idempotent.
- **`(ok)` means success**, per the LAV-78 rule: the renderer emits it when the key is absent, and absence of `is_error` means the call succeeded. So the stamp is 1 or 0 — never NULL, because a result *was* seen.
- **Contract risk, made loud**: the regex is a contract with the renderer at `claude_ai.py:105/112`. If that format changes, the command silently matches nothing — which looks exactly like success. Hence the `markers_seen` counter and an explicit warning when it is 0 with sessions present.
- **Local DB only** — no watermark, no sync — so run it on **each node**. Deliberately NOT added to `utils/services/lav-parser.sh`: it is a one-shot over a static export, not a per-cycle heal. Safe and necessary to re-run after `lav-parse-claude-ai --full`, which deletes and re-inserts the rows.

LAV-85 (part B): a quarter of the "errors" never ran — shared error taxonomy + outcomes on all six tables.
- **`is_error = 1` is not "the tool ran and failed".** Measured over a real corpus, **more than a quarter of bash errors are calls that never executed**: permission refusals, cancelled siblings (a parallel call in the same block failed, so this one was never dispatched), interruptions, and malformed calls the harness rejected. Counting them as failures inflates the Bash error rate by roughly a third and, worse, ranks tools by how often the user declines a prompt rather than by how often they break.
- **New shared classifier** in `queries.py` next to `_outcome_agg`: `_error_class_expr(alias, has_error_text)` maps a row to `sibling` / `denied` / `interrupted` / `rejected` / `failed` / `unknown`, and `ERROR_CLASSES_NEVER_EXECUTED` names the four that never ran. The class strings are Python constants used to GENERATE the SQL, so SQL, JSON and any frontend legend cannot drift. NULL for `is_error` 0 or NULL, mirroring `_outcome_agg`: a row that never failed has no class, and one that was never measured has none either — neither is "failed". `instr()`, never `LIKE`, so `_` and `%` inside a harness message cannot act as wildcards. Marker order is load-bearing: a cancelled-sibling payload quotes the command it cancelled and can contain the word "Permission", so sibling must win.
- **The markers were tuned against a real corpus, not guessed** — and the tuning mattered. The first pass left the majority of errors in `failed`; reading the ones with no `exit_code` surfaced four whole families that had been missed, including a second spelling of the single most common denial and a phrasing where an adverb sits between the two words of a marker (`require ... approval`). After tuning, the residual `failed`-with-no-exit-code is **under 1% of errors**, and those are genuine. Re-tune the same way: filter on class `failed` AND `exit_code IS NULL` and read what is left.
- **`error_text` added to the four thin tables** (`file_operations`, `search_operations`, `skill_invocations`, `subagent_invocations`) via `OUTCOME_COLUMNS`, which automatically extends `_ERROR_TEXT_TABLES`, `_migrate_add_tool_outcomes` and `_heal_tool_outcomes`. Without it those tables can report THAT a call failed but not HOW, so the taxonomy cannot separate a real failure from a denied permission.
- **`_outcome_agg` extended to the four functions that lacked it** — `get_files_stats`, `get_skills_stats`, `get_subagents_stats`, `get_searches_stats` — and `never_executed` + `errors_unclassified` added to **all six**, so every tool table now returns the identical outcome shape and a cross-table leaderboard can UNION them without special-casing any of them. Those four tables had never reported an error rate at all before this.
- **`errors_unclassified` is not decoration.** Between the migration (which adds `error_text`) and the backfill (which fills it) the column exists, every historical row holds `''`, everything classifies as `unknown`, and `never_executed` comes back **0** — reading as "none of these were denied" when the truth is "we have not looked yet". The second counter is what lets a caller tell those apart. For a table with no `error_text` at all both are NULL, never 0 — same rule as `is_error` NULL never meaning success.
- **`get_subagents_stats` also returns `by_spawn_tool`** (LAV-82), because the Task/Agent split is the only way to see from the dashboard that the table was frozen for months. The handful of rows written between the rename and the fix surface as their own `(unknown)` bucket rather than being folded into Task.
- **The CHILD_TABLES/OUTCOME_COLUMNS invariant is now enforced, not requested.** `backfill.py` has asked in a comment since LAV-78 that its column lists be kept in sync with `tool_outcomes.OUTCOME_COLUMNS` — and they drifted the moment `error_text` was added to four tables, silently, which is exactly the failure the comment warned about (the snapshot path simply stops shipping the column). `_assert_outcome_columns_shipped()` now checks it at import time and raises with the missing columns named. Verified it fires.

LAV-82: subagents stopped being recorded in **March 2026** — the parser only knew `Task`.
- **Problem**: `process_tool_call` matched the literal string `"Task"`. Claude Code renamed the subagent-spawning tool to **`Agent`** on 2026-03-01 and later added **`Workflow`**, so `subagent_invocations` quietly stopped filling while child agent sessions kept growing. Scanning a real transcript corpus: the last `Task` call predates the rename, and everything after it is `Agent`, with `Workflow` appearing from June. The dashboard's Subagents section had been showing a frozen February snapshot ever since.
- **Widening the tuple is not enough, and that is the subtle half.** The old branch was also gated on a non-empty `subagent_type`, and roughly 9% of `Agent` calls carry none (`mode`-only, `name`-only, or `resume`), while **no** `Workflow` call has one by construction. A naive `in ("Task","Agent")` fix still drops that 9% and 100% of Workflow, with no error and no counter. Hence a fallback ladder: `subagent_type` → `name` → `'(resumed)'` → `'(unspecified)'` for Task/Agent; `name` → `title` → **`meta.name` parsed out of the inline script** → `scriptPath` basename minus the generated `-wf_<id>` suffix → `'(inline-script)'` for Workflow.
- **One helper, two callers**: `tool_outcomes.subagent_row_from_tool_input()` is used by **both** `jsonl.process_tool_call` (which writes the row) and `tool_row_matches()` (which finds it again during backfill). Two copies of that ladder would eventually drift, and a drifted match key makes `stamp_tool_call_id()` stamp one call's outcome onto **another call's row** — the same failure `_bash_helpers()` exists to prevent.
- **New columns**: `subagent_invocations.spawn_tool` (`'Task'|'Agent'|'Workflow'`) + `.workflow_id`, and `interactions.workflow_id`, with `idx_subagent_spawn`, `idx_subagent_workflow`, `idx_int_workflow`. All three are derived **attributes**, deliberately kept OUT of the `UNIQUE(timestamp, session_id, project_id, subagent_type, description)` key — adding them would let the same call be inserted twice by two parser versions (same rule LAV-78 applied to `tool_call_id`).
- **`spawn_tool` seed is one-shot, with two belts.** Every row predating the migration was necessarily written by the Task-only branch, so it is provably `'Task'` — but a collector ingesting from an agent still on old code keeps shipping rows with an empty `spawn_tool` long afterwards, and re-seeding *those* as Task would be a lie. Guard 1: a `parse_state` flag (`schema:spawn_tool_seeded`, repo sentinels `project_id=-1, source='', host_id=-1`). Guard 2: a date bound at `SPAWN_TOOL_RENAME_DATE = 2026-03-01`. The few real rows dated after the rename are deliberately left `''` — "we do not know" is the honest answer there.
- **Workflow cohorts — the wf_ id was already on disk and was being thrown away.** Child transcripts live at `<parent>/subagents/workflows/wf_<id>/agent-*.jsonl`; the parent-extraction code anchored on the `subagents` path component and discarded the next two segments, which is why a multi-agent workflow was indistinguishable from that many unrelated spawns. It cannot be re-inferred from timestamps: a substantial minority of parent sessions ran more than one workflow. Now carried through `session_agent_info` into `update_interaction()`. **No `--since` is needed for the child side**: agent files bypass both the mtime skip and the per-message watermark, so a plain incremental parse re-reads every wf_ file and fills the column on the next run.
- **The parent invocation row recovers its cohort id from the tool_result**, which is what makes history reconstructable on both nodes with **no reparse and no sync**. The `Workflow` result announces its own transcript directory, and the LAV-78 `tool_call_id` correlation carries that back onto the row. New `workflow_id_from_tool_result()` is a **separate** function from `outcome_from_tool_result()` on purpose: that one returns early for successes and never flattens the body, and a workflow launch *is* a success. Applied from `process_tool_results()` (live path, including the out-of-order `pending` replay, whose tuple grew to 3) and from pass 2 of `lav backfill tool-outcomes`, which now also reports `workflow_ids_stamped`. `apply_workflow_id()` is **fill-only** — the value is immutable once known and a re-parse must not be able to downgrade it.
- **`update_interaction()` is INSERT OR REPLACE over the whole row**, so a new column omitted from its list is silently reset on every parse — the symptom (correct after a targeted reparse, empty an hour later) reads like a sync bug. Beyond adding the column, `workflow_id=None` now means "caller does not know — keep what is stored" while `""` means "caller knows there is none — clear it". The codex and cowork call sites pass neither and can never be workflow children, so today the distinction changes nothing; it exists so that the NEXT caller added to this function cannot silently wipe the column.
- **The snapshot path heals `workflow_id` on sessions the collector already has.** `copy_interactions()` is `INSERT OR IGNORE`, so a child session pulled before this ticket keeps its old row with `workflow_id` `''` — and a normal pull can never fix it, because its timestamp is far behind the export cursor. Without the heal, the collector's cohort view stays permanently empty while the agent's is complete, which reads as a sync bug and is not one. Fill-only (the id comes from a path that exists only on the agent's disk, so an older agent sending `''` must not be able to erase it), batched in one pass over the snapshot, and guarded with `try/except OperationalError` so an agent predating LAV-82 simply has nothing to heal.
- **Verified end to end on real corpora**: a project with two workflow runs went from **0 rows** to one invocation per run, each labelled from the script's `meta.name` and linked to its cohort of child sessions; a project spanning both tool generations records `Agent` and `Task` rows correctly separated by `spawn_tool`, where the `Agent` ones were previously lost entirely. Zero false positives in both directions (no non-workflow agent child got an id, no top-level session got one). Helper unit cases covering every input shape observed in the corpus pass; the migration is idempotent and its re-run is silent.
- **Sync**: `spawn_tool`/`workflow_id` are taken from the payload and **not** re-derived — unlike `kind` they are not functions of columns that travel (one comes from the `tool_use` name, the other from a `tool_result` the collector never sees), so the agent is the only source. `backfill.py` `CHILD_TABLES` and `INTERACTION_COLUMNS` gain them so the snapshot path carries them too.

LAV-85 (part A): `mcp_tool_calls.kind` — the "MCP Tools" chart was mostly not MCP.
- **Problem**: `mcp_tool_calls` is not "MCP calls", it is the catch-all for every tool call with no dedicated table — so both export parsers pour the **host's own built-in tools** into it. `chatgpt.py` hardcodes `server_name='chatgpt'` for OpenAI's built-ins (browsing, code interpreter, image generation, file search, plus obfuscated internal namespaces); `claude_ai.py` writes the integration name or the literal `'claude_ai'` for Anthropic's (artifacts, repl, the bash tool, the text-editor commands). On a real corpus that is a large fraction of the table — none of it MCP, none of it carrying any outcome data (those exports have no per-call `tool_result` linkable to the row, so `is_error` is NULL **by design**). It is also why the table's apparent `measured` coverage looks far worse than the coverage over real MCP servers alone.
- **New column `kind TEXT DEFAULT ''`** (`'mcp'` | `'builtin_host'`) + `CREATE INDEX idx_mcp_kind ON mcp_tool_calls(kind, server_name)` — `(kind, server_name)` and not `(kind)`, because every query that splits the two worlds then groups by server inside one of them. The index is created in `_migrate_add_tool_kind`, **not** in the `SCHEMA` literal, for the same reason as `idx_bash_cmd_name` (LAV-79): `CREATE TABLE IF NOT EXISTS` cannot add a column to an existing table, so indexing it there aborts the whole `executescript` on every existing DB.
- **A whitelist on `server_name` would be wrong in BOTH directions — measured, not assumed.** `server_name='claude_ai'` is a **mixed** bucket: a meaningful share of its rows are real connector calls whose `integration_name` was absent on that content block. And in the opposite direction, servers whose name merely *starts with* `claude_ai_` are **real MCP servers seen from Claude Code** (`mcp__claude_ai_<server>__*`, split by `process_tool_call`) — a `server_name LIKE 'claude_ai%'` rule would put them on the wrong side of the wall. Hence `tool_outcomes.tool_kind(session_id, server_name, tool_name)` is **conjunctive**: the session prefix (`chatgpt:` / `claudeai:`, stamped by the export parsers) says which host produced the row, and only then does the tool-name whitelist get a vote. A connector that genuinely names a tool `web_search` can never be caught, because it would not be in a `claudeai:` session with `server_name='claude_ai'`.
- **The whitelist is deliberately conservative, and membership was decided by evidence.** A tool that ALSO appears in the corpus under an explicit integration/server name is a connector tool that merely lost its `integration_name` on some blocks — that check removed two note-related tools that also show up under a third-party notes server, and kept out several generic-sounding names for which there is no positive evidence either way. The asymmetry is the point: a connector wrongly marked `builtin_host` **disappears** from the MCP view (a silent lie), while a builtin left as `mcp` merely shows up with `measured = 0`, which the `measured` badge already explains and a reader can spot.
- **`tool_kind()` is TOTAL** — it never returns `''`. So `kind = ''` on a DB `init_db()` has touched means the migration **failed**, not "unknown", and the resume probe on every later `init_db()` is an empty index seek instead of a scan.
- **Migration `_migrate_add_tool_kind`** (wired into `init_db` after `_migrate_add_cmd_name`, same print-and-continue style), three passes that reproduce `tool_kind()` exactly: `chatgpt:` rows in pure SQL (that branch consults nothing else); `claudeai:` rows through **`tool_kind()` itself in Python**, paged by id; everything still `''` → `mcp`. The middle pass is Python on purpose — expressing `split(':')[-1]` in SQLite means an unreviewable `rtrim`/`replace` idiom, and calling the real function makes drift between migration and parser impossible. That subset is small enough that the loop is free.
- **Verified on a copy of a real database**: every row classified, **none left unclassified**; every `claude_ai_*` MCP server correctly stayed `mcp`; **no** row outside a `chatgpt:`/`claudeai:` session was marked `builtin_host`; the claude.ai rows left as `mcp` are exactly the real connectors. Re-running `init_db()` prints nothing and writes nothing. **Fresh-vs-migrated parity checked explicitly**: identical `PRAGMA table_info(mcp_tool_calls)` on both paths, and `idx_mcp_kind` present on both.
- **Write sites**: `jsonl.py` claude_code + codex branches (both call `tool_kind()` rather than hardcoding `'mcp'`, so there is exactly one place that decides what `kind` means), `chatgpt.py` (literal `'builtin_host'` — the ChatGPT export has no notion of MCP at all), `claude_ai.py` (must go through `tool_kind()`: the shortcut `'builtin_host' if not integration else 'mcp'` is exactly the mistake the mixed bucket punishes). **Sync ingest RECOMPUTES `kind` locally** instead of trusting the payload — same rule LAV-79 applies to `cmd_name` — which makes agent/collector version skew a non-issue in both directions. `backfill.py` `CHILD_TABLES` gains the column so the snapshot path carries it too.
- **New `lav backfill tool-kind [--reclassify]`**: normally redundant, since `init_db()` derives `kind` on every parse and every server start on every node. It exists for the one case the migration cannot handle — the migration only ever **fills blanks**, so editing `CLAUDE_AI_BUILTIN_TOOLS` has no effect on already-classified rows. `--reclassify` blanks the column first. Verified deterministic: a full `--reclassify` reproduces the identical split.

LAV-84: the Source filter made `/api/data` take **minutes**. One character fixes it.
- **Problem**: `build_filters()` emits `ss.source = ?` (`queries.py`) against the `LEFT JOIN session_sources` that `_join_session_sources()` produces. That WHERE term rejects NULL, so since SQLite 3.39 the planner strength-reduces the LEFT JOIN to an INNER one and is free to reorder the two tables — and it chooses `idx_session_sources_source` as the **outer** loop, probing the tool table once per matching session. Measured on a multi-GB database with a source filter and no date bound, two of the legs took **over 90 seconds each** (`SEARCH ss USING idx_session_sources_source` → a per-project range scan / a scan over a covering index). Two other legs came in at ~20ms — same query shape, the planner just happened to pick the right order. Pre-existing since the source filter was introduced; nothing to do with any dashboard work.
- **Fix**: `clauses.append("+ss.source = ?")`. SQLite's unary `+` is value- **and** type-preserving; its only documented effect is that the term can no longer drive an index. The planner therefore keeps the tool table as the outer loop and probes `session_sources` by its primary key. **Both slow legs drop to well under a tenth of a second — roughly three orders of magnitude — with identical row counts verified on both plans.** Through the real code path, the two affected stats functions with a source filter go from minutes to **under a second including Python startup**. NULL handling is unchanged: `+NULL = 'x'` is still NULL, so a tool row with no `session_sources` match is still rejected exactly as before.
- **Why the `+` and not an `EXISTS` rewrite**: `EXISTS (SELECT 1 FROM session_sources ss WHERE …)` is comparably fast and more readable, but every caller of `build_filters()` currently assumes a pre-joined `ss` alias, so it would need a second variant of the function and a sweep of all seven `get_*_stats`. The one-character version is documented in place with the measured plans on both sides, precisely because it looks like a typo.
- **Not applied to `search_messages`** (`queries.py`, which builds its own WHERE list): measured essentially unchanged before and after — there the `m.content LIKE '%…%'` scan dominates and the join order is irrelevant. Changing it would have added noise for no gain.

LAV-80: `bash_commands` records **100% of shell**, and `lav-parse --since` can go back and get the history.
- **Problem**: `bash_commands` stored a row only when the **first word** of the command was one of the 24 in the `FILE_COMMANDS` whitelist (`is_file_related_bash`, `config.py:58`). Measured on the real DB: **15.872 of 63.982** Bash `tool_use` blocks passed — **24,8%**; the other 75,2% were never recorded at all. `cd` alone accounted for 17k of the losses, and every compound command opening `cd … && …` was invisible, which meant build, test, git and network work was invisible. LAV-78 made that gap actively dangerous: it published an `error_rate` on a table that looked complete and was not.
- **The gate is gone** (`jsonl.py` `process_tool_call`): the insert now takes any Bash call with a non-empty `command` (non-`str` payloads coerced, whitespace-only dropped — 4 rows in the whole corpus). **+47.316 rows, +3,05x logical content.** 93,7% of Bash calls carry a `tool_result`, so `is_error` coverage on the new rows is near-total. **The published Bash error rate moves 4,99% → 5,79%** and finally deserves the name. Rates that were structurally unobtainable become available and are not flat: `sshpass` 24,1%, `python` 16,6%, `node` 15,4%, `npx` 14,2%, `gh` 13,9%, `ssh` 10,8%, `source` 10,9% — against `grep` 1,7%, `sed` 1,7%, `wc` 1,2%. That spread is the justification for the ticket.
- **`file_operations` is byte-identical — proven twice, not assumed.** The same gate feeds the Bash-derived `file_operations` rows, so the risk was writing garbage into a healthy table. `BASH_READ ∪ BASH_WRITE ⊆ FILE_COMMANDS` and `extract_target_file`'s 11 commands `⊆ FILE_COMMANDS` were re-verified as set inclusions; over the **48.110 real non-file-related commands**, `get_bash_category()` returned non-`None` **0 times** and `extract_target_file()` **0 times**, so **0 rows** could reach the `file_operations` INSERT. End to end on 4 real project dirs copied to `/tmp` (323 transcripts, two scratch DBs): `file_operations` **1069 rows / sha256 4e43fcbf…e8c8** before and after — identical, `BashRead`=21 / `BashWrite`=2 included; `messages`, `search_operations`, `interactions`, `mcp_tool_calls`, `token_usage`, `skill_invocations`, `subagent_invocations` identical too; `bash_commands` 251 → **756**, old rows a byte-identical strict subset, and a second incremental parse still 756 (the `NOT EXISTS` guard holds). Exhaustively, all 63.982 real Bash calls driven through `process_tool_call`: `file_operations` **2812 / d6358817…5dcc** on both sides.
- **New column `cmd_name TEXT DEFAULT ''`** + `CREATE INDEX idx_bash_cmd_name` — the program the command actually runs, derived in Python by `bash_cmd_name()` (`jsonl.py`). It walks separators (`&&`, `|`, `;`, `$(…)`) and hops over `cd`, `env`-style `VAR=x` assignments and wrappers (`sudo`, `nice`, `time`, `xargs`, `nohup`, …, including flags that take a detached argument, so `nice -n 19 ffmpeg` → `ffmpeg`, not `19`), then basename-normalises. Measured over all 63.982 commands: **303 buckets, 99,86% usable, `cd` = 0, 3,4 µs/command** — versus the naive first token's 901 buckets, 69,53% usable and `cd` = 17.220. Top-20 covers 86,6%. The 89 residual unusable rows (0,14%) are `(var)`, a bare `\`, `''`, `:` and one-off parse artefacts. `''` means **"derived, undecidable"** and is a real answer; the column is never NULL on a DB `init_db()` has touched. Correctness: 20.000 randomly sampled rows re-derived, **0 mismatches**. Fresh-vs-migrated divergence checked explicitly — `PRAGMA table_info(bash_commands)` is identical on both paths, and fresh DBs get the index because the migration runs inside `init_db`.
- **Cost, measured, not extrapolated**: +27,6 MB of rows (583 B/row — non-file commands are longer: mean 394 vs 318 chars) plus +4,6 MB for `cmd_name` and its index ≈ **+32 MB on a 5,4 GB database, 0,6%**. The table triples logically (19.187 → 62.805 distinct keys) but grows only ~1,8x physically, because 39k of today's 58k rows are pre-LAV-66 duplicates. The `NOT EXISTS` insert guard is **not** the unindexed correlated subquery it was assumed to be: `idx_bash_timestamp` already covers it (`SEARCH … USING INDEX idx_bash_timestamp (timestamp=?)`), measured 0,024 ms/row at today's 58k, **0,022 ms/row at 110k, 0,030 ms/row at a 330k stress size** — B-tree, O(log n), ~1,4 s of guard time for the entire 47k historical recovery. **No index was added for the guard** (tested: a `(session_id, project_id, timestamp)` index makes the planner switch and inserts 2x slower, for no read-side gain). The one index that was added costs **+0,003 ms/row (+11%, ≈0,14 s over the whole recovery)** and takes the dashboard `GROUP BY cmd_name` from **433,8 ms to 11,9 ms** (`SCAN … USING COVERING INDEX idx_bash_cmd_name`).

Everything degrades gracefully on an unmigrated DB via `PRAGMA table_info` — which is exactly why `cmd_name` is a **real** column and not a `GENERATED` one: `table_info` does not report generated columns, so the guard would have read "not migrated" forever. `_BASH_CMD_TYPE_CASE` (the 17-branch `LIKE` ladder) survives only as that fallback. **`total_bash` and the daily line ~3x — this is the fix, not a regression**; the daily chart now means "shell calls/day" instead of "file-ish shell calls/day".

- **New `lav-parse --since <ISO>`** — bounded, additive re-read. It temporarily **lowers** the incremental watermark so the parser re-opens files it would have skipped; it inserts only, deletes nothing, and every insert is duplicate-guarded, so re-running a window is a no-op. Accepts `2026-06-01` or `2026-06-01T00:00:00Z`, normalised **once** in `main()` to the exact 24-char `YYYY-MM-DDTHH:MM:SS.mmmZ` shape the stored watermarks use (381/381 of them) — without the milliseconds the lexicographic compare would put `'Z'` (0x5A) after `'.'` (0x2E) and silently land past the same second. Rejected together with `--full`, which is the destructive path and already ignores the watermark; `--project` composes.
- **`--since` can never lower a persisted watermark** — the guard is the point of the feature, and the naive version regresses on both the claude_code and the codex path (reproduced). The write-back is seeded from the **stored** value, not the lowered one, and only fires when it would move the watermark **forward**; the effective window is `min(stored, since)`, so a `--since` *newer* than the stored value widens nothing. On codex the pre-existing write-back guard was **not** sufficient (it compared against the already-lowered in-memory watermark), and 31 of the 44 production codex watermarks are legacy naive `datetime.now().isoformat()` strings, so that path compares aware-UTC `datetime`s, never strings. Verified on a frozen corpus: a re-parse with the watermark lowered 30 days produced a **byte-identical DB** (count + content hash on all 10 tables), and deleting every in-window row then re-running restored the **exact original state, hash for hash**. Agent files (LAV-65/66) are unaffected — both mtime and message gates are already `not is_agent_file`, so `--since` changes only the value they compare against.
- **Codex `mcp_tool_calls` duplication — fixed first, because `--since` would have doubled it.** The codex `list_mcp_resources` / `list_mcp_resource_templates` / `read_mcp_resource` branch inserted with `INSERT OR IGNORE`, and `mcp_tool_calls` has **no UNIQUE constraint** — so `OR IGNORE` had nothing to fire on. Reproduced synthetically: 2 rows after run 1, **4 after a second pass**. Converted to the `INSERT … SELECT … WHERE NOT EXISTS (timestamp, session_id, project_id, tool_name)` form the claude_code branch already uses. Blast radius today is zero (0 such rows in prod), which is what made it a free fix.
- **Recovered rows do NOT travel to the collector — run `--since` on every node.** They keep their **original** timestamps, which sit far below the collector's `last_pull` cursor, and `export_sessions` pages child rows by the tool call's own timestamp, so a normal push-triggered pull will never ship them. Same structural drift LAV-78 documented for outcomes, same remedy: per-node execution (the alternative, `pull_from_agents(full=True)`, re-exports the entire history at a much higher cost). A `--since` run still fires `notify_collector()` at the end — harmless, and it achieves nothing for these rows.
- **Scope boundary**: removing the gate only affects **newly parsed** content. The 47.316 historical rows appear when someone runs `lav-parse --since <ISO>` over the window that contains them — no `--full`, no SQL on `parse_state`. LAV-78 is strictly better off under `--since`, not worse: `apply_tool_outcome` is keyed on `(session_id, project_id, tool_call_id)` and derives `duration_ms` in SQL from the row's own timestamp, so re-applying writes identical values (verified unchanged across a re-run on `bash_commands`, `file_operations` and `search_operations`), and the per-file `pending_tool_results` buffer is replayed for every reopened file, so a `tool_result` orphaned by an mtime skip finally finds its row.
- **The coverage caveat that survives** — this one is real, measured and permanent. After a **full** `lav backfill tool-outcomes`, **26,1%** of `claude_code` `bash_commands` rows still have `is_error IS NULL`, because **14.795** of them have no `tool_use` block in `messages` at all: append-only rows from an earlier parser era whose source blocks were never stored, and nothing can reconstruct them. They are a permanent hole in the **denominator**, which the `_outcome_agg` contract already handles (NULL is excluded from `measured`, never counted as success). Crucially it is **symmetric between agent and collector** — both sides derive outcomes from their own `messages` — so it is a coverage cap, **not** agent/collector drift. Separately: the scheduled self-heal in `utils/services/lav-parser.sh` runs on a **bounded lookback window** (`LAV_BACKFILL_LOOKBACK_HOURS`, default 72h); a collector outage longer than the window leaves those rows NULL permanently until someone runs `lav backfill tool-outcomes` once **without** `--since`.
- **Consistency fix — `_nonneg_int` on the read path too** (`cli.py`): LAV-78 added it to `lav backfill --limit/--progress-every` because SQLite reads a negative `LIMIT` as "no limit". `lav search --limit` and `lav kb search --limit` were still bare `int` with the same hazard — reproduced: `--limit -1` returned the entire table (5/5 rows on a 5-row scratch DB, vs 2 for `--limit 2` and 0 for `--limit 0`). Read-only, so not a blocker, but guarding the write path and leaving the read path open was indefensible. Both now reject negatives at parse time; `0` still means literally zero.
- **Retired**: the LAV-78 caveat "`bash_commands` is not all Bash, its error rate is the error rate of copying and listing files" (`CLAUDE.md`, `README.md`, and the LAV-78 entry below) is now false and has been rewritten everywhere it appeared. A stale caveat that understates the data is as misleading as a missing one.

LAV-78: tool calls now record their **outcome** — status, error text, duration (first slice of `docs/otel-gap/02` §A4).
- **Problem**: the six tool tables (`file_operations`, `bash_commands`, `search_operations`, `skill_invocations`, `subagent_invocations`, `mcp_tool_calls`) recorded WHAT an agent invoked, never HOW IT WENT. The outcome survived only as raw text inside `messages.content`, unlinked from the call that produced it — "which tools fail, and how often" was unanswerable in SQL (the interaction view re-paired `tool_use`↔`tool_result` by hand from the raw JSON).
- **Schema** (additive): all six tables gain `tool_call_id TEXT DEFAULT ''` (`toolu_*`/`call_*` — correlation only, **never a key**: 3,0% of the ids are duplicated at the source), `is_error INTEGER` and `duration_ms INTEGER`; `bash_commands` and `mcp_tool_calls` also `error_text TEXT DEFAULT ''` (written only on error, capped at 2000 chars); `bash_commands` also `exit_code INTEGER` — not a field in any source, parsed with `^\s*Exit code (\d+)` off the result text (matches 73% of the Bash errors; the rest are permission-denied/blocked, which have no exit code). Plus 6 partial indexes `idx_<t>_tool_call ON <t>(session_id, project_id, tool_call_id) WHERE tool_call_id != ''`. **No `NOT NULL` anywhere**: SQLite forbids `ADD COLUMN NOT NULL` without a constant default, and every parser writes with `INSERT OR IGNORE`, where a constraint violation silently discards the row (LAV-77 finding).
- **New module `lav/tool_outcomes.py`** — single source of truth for the column list (`OUTCOME_COLUMNS`) and the index DDL, iterated by **both** the `SCHEMA` literal and the migration, so a fresh DB and a migrated DB cannot diverge. Also holds the `tool_use`→row routing (a file-related Bash writes to **two** tables), the `tool_result` reader, and the two writers. Stdlib + `lav.config` only: `jsonl.py` imports it, so it must never import `jsonl` back (the three bash helpers are imported lazily inside the one function that needs them).
- **`is_error` semantics — the 0-vs-NULL rule**: `0` = a `tool_result` exists and carries no `is_error` key — measured, **the absence of the key means success** (345 keyless successes over 80 transcripts); `1` = flagged error; `NULL` = **no `tool_result` was ever seen** (truncated transcript, or a parser that reads none). NULL is never "assumed success": every error-rate query must exclude NULL from the **denominator**. This corrects the "NULL = unknown" semantics written in `02-db-evolution-plan.md` §A4 (already contradicted by `07-numeri-e-insidie.md` §1.4).
- **`duration_ms`**: wall clock between the record carrying the `tool_use` and the one carrying the `tool_result`, computed **in SQL** against the row's own timestamp so it stays correct across incremental runs (the call is parsed in run N, the result can arrive in run N+1). Native duration fields exist in only 1,4% of the results — not modellable; the derived delta is available ~100% of the time. It **includes** permission-prompt wait and background tasks (measured p50 1,0s, p90 5,8s, p99 157s, max 76 min): the tail is real signal, so it is not clamped — only negative or absurd values (>7 days — clock skew, mis-pairing) fall back to NULL.
- **Coverage**: populated by the parsers that actually see `tool_result` blocks (claude_code, cowork) and propagated by the collector sync ingest. `claude_ai` and `chatgpt` rows stay **NULL** — those exports carry no per-call result linkable to the row; Codex too, its `function_call_output` exists in the rollouts but is not read today (§A7). Measured on 80 real transcripts: `tool_use`↔`tool_result` pairing 99,98% (5.552/5.553), error rate Bash 3,1% (93/3.029), MCP 5,1% (25/487).
- **What `bash_commands` did NOT measure — ⚠ SUPERSEDED BY LAV-80, which ships in this same release; kept for the record only.** As written here, `bash_commands` gated the insert on `is_file_related_bash()` and kept a call only when the **first word** of the command (basename-normalised, so `/bin/ls` counts) was one of the **24 entries** in the `FILE_COMMANDS` whitelist (`lav/config.py:58`) — `cat head tail less more cp mv rm mkdir touch ls find tree chmod chown tar zip unzip sed awk sort wc diff patch`. Measured on the LAV-78 collector DB: **15.762 of 63.522** Bash `tool_use` calls produced a row — **24,8%**; the other **75,2% were never recorded at all**. The biggest blind spots, by first word: `cd` 17.156, `grep` 5.592, `git` 3.651, `python3` 3.212, `ssh` 2.850, `open` 1.554, `curl` 1.409 — build, test, git and network work entirely invisible, and so was every compound command opening with `cd … && …`. The consequence recorded here, that the `error_rate` this ticket exposes is the error rate of copying and listing files and **not** the error rate of Bash, was the reason LAV-80 was opened immediately after: the gate is now gone, the table holds 100% of shell, and the honest Bash error rate is **5,79%** (it read 4,99% under the whitelist). Do not quote the 24,8% cap as current behaviour — see the LAV-80 entry above.
- **Backfill**: new `lav backfill tool-outcomes` walks the 183.728 messages containing a `tool_use_id`, stamps `tool_call_id` on pre-existing rows that have none (`AND (tool_call_id IS NULL OR tool_call_id = '')` — it never overwrites) and applies the outcome. Idempotent and re-runnable, scopable (`--since/--project/--source/--limit`, `--dry-run` rolls back). Runs on the **local** DB only — no reparse, no `parse_state` watermark touched — so it must be run on **each node**: the collector's sync ingest is `NOT EXISTS`-guarded and never updates a row it already has.
- **Snapshot path** (`lav/backfill.py` `CHILD_TABLES`): the ssh+`.backup` alternative to the HTTP pull now ships the new columns too — a stale list there would make the outcome silently *not* travel. Deploy note: the **agent** must have the columns before the collector runs a snapshot backfill against it, otherwise the `SELECT` fails with `no such column`.
- **Review fix — outcome drift never reached the collector** (`queries.py` `export_sessions`): child rows ship under `AND timestamp > ?` inside `batch_load()`, where the timestamp is the **tool call's own** time, not an update time. The interaction-level filter was fixed long ago (LAV-46/LAV-49, `COALESCE(m.last_msg_ts, c.timestamp)`); the **child-level** one was never touched — and until this ticket it was *correct*, because child rows were immutable. `is_error`/`duration_ms` are the first mutable columns in those tables, and the two-run ordering LAV-78 depends on breaks the cursor: run N parses a `tool_use` with no `tool_result` on disk yet (`is_error` NULL), ships the row, cursor advances past that timestamp; run N+1 stamps the outcome onto a row whose timestamp is now **behind** the cursor, so it never re-ships — and the collector's `NOT EXISTS` ingest guard would skip it even if it did. Continuous, accumulating divergence between agent and collector, not a one-off historical gap. **Closed operationally**: the scheduled parser (`utils/services/lav-parser.sh`) now runs `lav backfill tool-outcomes` after the parse on **every node**, so the collector re-derives outcomes from its own `messages` instead of waiting for them to travel. The export cursor itself is unchanged — child rows are still filtered by the call's own timestamp, which is why the backfill has to run on both sides.
- **Review fix — `tool_result` stored *before* its `tool_use`** (`jsonl.py` `process_tool_results`): results were applied inline in raw file order, with no pending buffer and no rowcount check, so a result whose record sits **earlier in the file** than the call it answers matched zero rows and left `is_error`/`duration_ms` NULL for good — and `--full` could not repair it, since the file order is identical on every reparse. Real, not theoretical: reproduced on `951c2618-5bd9-43d0-9d83-ce43e15d9141.jsonl`, where line 52 carries the result for `toolu_016uNjdYKkJyngtM6nE3GuMi` and line 53 carries its `tool_use`. Unmatched results are now held and re-applied once the file has been read.
- **Review fix — `lav backfill --limit 0` silently meant "no limit"** (`cli.py` `_bf_session_query`): the `LIMIT` clause was guarded by truthiness (`if limit:`), so `--limit 0` emitted exactly the SQL of omitting the flag and swept **every** session in write mode, while the JSON result still reported `"limit": 0`. Reproduced end to end. `0` is no longer equivalent to unlimited.
- **Deliberately NOT done**: open decision **A1** (`docs/otel-gap/00-stato-e-decisioni.md` — one unified `tool_calls` table + 6 compat views vs 18 `ALTER TABLE`) stays open; this ticket takes the additive route without settling it.

LAV-39: Fix double-counting of Claude Code costs/tokens on multi-block turns.
- Claude Code writes one JSONL record per content block (`thinking`, `tool_use`, text) but all blocks of a single API turn share the same `message.id` and `usage`. The parser was summing usage per row, inflating `cost_usd` and `total_tokens` by ~20–35% on Opus sessions with thinking.
- `messages` and `token_usage` gain an `api_message_id` column; new partial `UNIQUE(session_id, project_id, api_message_id)` index on `token_usage` makes `INSERT OR IGNORE` idempotent per API turn.
